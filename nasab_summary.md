## What Nasab is

Nasab is a Flutter (iOS + Android) family archive app. Users create or join a family, add family members, build a family tree (parents/spouse/children, now in three switchable layouts), get an auto-generated timeline (births, deaths, marriages), post photo/video/audio "memories" with captions and voice notes, organize memories into albums, tag members, comment and like, and manage member profiles. A Free tier is fully usable from signup; a paid **Heritage** tier (via RevenueCat) unlocks higher storage, higher-quality compression, voice notes, video, the radial tree view, and unlimited albums. Backend is Supabase (Postgres + Auth + Row-Level Security) for data/auth, with Firebase Storage for media files, Firebase Remote Config, and PostHog for analytics. Firebase Auth is deliberately not used — the app relies solely on Supabase Auth, and every Storage read/write is gated by a client-side RLS check against Supabase first.

Current app version: **0.3.2+59**.

## Architecture

Feature-first, three layers per feature, no separate "usecase" layer:
- `domain/` — entities and abstract repository interfaces, pure Dart.
- `data/` — models, `XyzRemoteDataSource`, `XyzRepositoryImpl` (the only layers besides `providers/` allowed to touch `supabase_flutter`/`firebase_storage` directly).
- `presentation/` — `screens/`, `widgets/`, `controllers/` (Riverpod codegen `AsyncNotifier`/`Notifier`, named `XyzController`). Screens/widgets only ever call controllers, never datasources or SDKs directly.

State management is Riverpod with code generation (`@riverpod`). `lib/providers/` is the single place dependency-wiring providers live (Supabase/Firebase singletons, per-feature datasource/repository providers, app-wide session/family state) — all `@Riverpod(keepAlive: true)`. `lib/services/` holds cross-cutting wrappers (shared prefs, logging, remote config, storage, analytics, permissions, connectivity, deep links, push notifications, subscriptions, device info, media compression, media job queue), each with a matching keepAlive provider. `lib/styles/` is the single source of truth for colors, typography (Fraunces/Lora/Inter via `google_fonts`), buttons, spacing, radii, and theme — nothing hardcodes a color or `TextStyle` inline. User feedback (errors/confirmations) goes through a custom `AppToast`, never `ScaffoldMessenger`/`SnackBar` directly. Every DB table/column name used in Dart is a constant in `lib/core/constants/db_constants.dart` — no magic strings in datasources. Routing is `go_router` with a `StatefulShellRoute.indexedStack` bottom-nav shell.

**18 feature directories** under `lib/features/`: `auth`, `family`, `family_statistics`, `feedback`, `home`, `invite`, `member_groups`, `members`, `memories`, `notifications`, `onboarding`, `permissions`, `profile`, `relationships`, `settings`, `subscription`, `timeline`, `tree`.

- `features/permissions/` remains a real, populated feature (runtime-permission priming screen/controller).
- `features/member_groups/` unchanged: personal, per-user shortcut groups of family members used for quickly selecting recipients/tags.

## Feature-by-feature state

- **Auth** — Email/password (two-step bottom-sheet flow) plus Google and Apple social sign-in. A server-side `check_email_exists` function backs a single unified sign-in/sign-up screen.
- **New: Location picker.** A new `lib/core/location/` module (own domain/data/presentation triad — `PlaceSuggestion` entity, `PlaceRepository`, `GooglePlacesRemoteDataSource`, `location_providers.dart`) backs a shared `showPickLocationSheet`/`LocationPickerField` — a debounced, Google Places–backed city/country search sheet (min 3 chars) requiring a new `GOOGLE_PLACES_API_KEY` dart-define. Used for a member's `current_location` (new `family_members` column, shown via `MemberLocationRow` on the profile screen, editable inline) and for `place_of_birth`/`place_of_burial` in Add/Edit Member. A new `events.location` column gives every timeline event a location too: birth/death event location auto-syncs from place of birth/burial (same pattern `event_date` already uses for dob/dod), while marriage events get their own location, settable at creation and editable afterward via a narrow direct `EventRemoteDataSource.updateEventLocation` write. Backed by the `add_member_and_event_locations` migration.
- **Family creation & invite/join** — Create a family or join via invite code; a Postgres RPC (`create_family`) seeds the account holder as a claimed default member. Joining via invite code can claim an existing unclaimed member row instead of always inserting a new one, with a DB-enforced limit on how many families a user can create/join. **Invite codes were single-use by a default-value bug** (`create_family_invite` defaulted `p_max_uses` to 1, never overridden from Dart) — every invite after the first redemption failed with "This invite has already been used." Fixed by raising the default to 200 uses per invite; existing invite rows are unaffected. `list_unclaimed_members` now also surfaces a claimable member's spouse name, to help the right relative pick their own row. A new pair of RPCs, `unclaim_family_member` (owner-only) and `claim_existing_member` (self-serve), let a wrongly-claimed row be detached and re-claimed correctly without deleting the row or losing its relationships/timeline/memories — a lighter-weight fix path than `remove_family_member`'s hard delete.
- **New: Deep linking overhaul (ChottuLink, deferred deep links).** Invite-link handling moved off the previous plain `app_links` Universal/App Links implementation onto the **ChottuLink** SDK (`chottu_link: ^1.1.3`), replacing the earlier hosted domain `nasab.tappstudio.in` with a dedicated `nasab.chottu.link` for the `/f/<code>` invite path everywhere it's referenced (Android `AndroidManifest.xml` intent filter + a new `flutter_deeplinking_enabled=false` meta-data entry to stop Flutter's own auto-handling racing the native SDK, iOS `Runner.entitlements` associated domain, `DeepLinkService`, `InviteShareScreen`). The headline capability gain is **deferred deep linking**: a code tapped in an invite link survives a fresh install (App/Play Store round-trip) and is recovered on first app open, not just on warm/cold start with the app already installed — closing an explicit MVP1/MVP2 gap ("deferred deep linking (e.g. Branch.io-style)" was previously listed as out of scope). `DeepLinkService` drops its old `codeFromUri(Uri)`/`getInitialCode()` split in favor of a single `codeStream` sourced from `ChottuLink.onLinkReceivedWithMeta`, parsed from `ResolvedLink.shortLinkRaw`/`shortLink` (the actual tapped `nasab.chottu.link/f/<code>` URL, not `ResolvedLink.link`, which is a separate per-link browser/store-fallback destination). `InviteShareScreen` now calls `ChottuLink.createDynamicLink` after generating an invite to mint a real `nasab.chottu.link/f/<token>` short link (with social title/description metadata) and prepends it to the shared invite text, falling back silently to code-only sharing if link creation fails; the link's configured fallback destination points at a `nasab-landing` web page (`nasab.tappstudio.in/f/?code=<token>`, a separate repo, not part of this codebase) for a visitor without the app installed. `main.dart` now awaits `ChottuLink.init(apiKey: Env.chottulinkApiKey)` early in boot (unlike the other, deferred-initialized SDKs) since a deferred link's recovery depends on the native SDK being ready before `DeepLinkService`'s listener attaches. New `CHOTTULINK_API_KEY` dart-define and `Env.chottulinkApiKey`. A new **`preview_family_invite_public`** Postgres RPC (anon-callable, narrower than the existing in-app `preview_family_invite`: no `family_id`, just `family_name`/`is_valid`) backs that same `nasab-landing` fallback page showing "Join the &lt;Family&gt; family" to a signed-out visitor before they install.
- **Family members** — First/last name, optional date of birth, country code (added then dropped), `place_of_birth`/`place_of_burial`, contact fields, `is_deceased`, denormalized father-name fields for patronymic display, member deletion, `added_by`. Deceased members are excluded from the "unclaimed members" list. An **avatar thumbnail** column/pipeline (separate from full-res profile media, used across tree nodes, member list, celebrations card, invite claim tiles) backs fast list/card rendering. `family_members.linked_user_id`/`added_by` are `ON DELETE SET NULL` against `auth.users` (previously plain `NO ACTION`, which blocked deleting an auth user linked to or having added a family member). **Avatar cropping** — every avatar entry point (Add/Edit Member, Onboarding) routes through a shared `pickAndCropAvatar` helper (`lib/core/media/avatar_picker.dart`, `image_cropper: ^11.0.0`) that opens a native circular 1:1 crop UI (uCrop on Android, `TOCropViewController` on iOS) with pinch-to-zoom/pan after the gallery pick. Avatars are quota-tracked: they get a real `media` row (`media.is_avatar` boolean) so avatar bytes count toward `family_storage_used_bytes` like every other upload, while staying excluded from the profile-gallery fetch/count and its 5-photo cap; swapping an avatar nets the outgoing file's size out of the quota check so a family at quota can still replace a similarly-sized avatar, and member deletion separately cleans up the avatar's Storage files.
  **New: in-married gating ("request & approve" for gated branches).** A permanent `family_members.married_in` boolean flags any member who entered the tree via a spouse relationship rather than blood descent from the family's founding root (set once at creation by `MemberController.addMember`'s `markAsMarriedIn` param, backfilled by one-time heuristic for pre-existing rows, never recomputed from tree topology afterward). A separate `gated_branch` boolean — true for every `married_in` member and inherited by anyone added underneath them via this flow — propagates the approval requirement indefinitely up the ancestral branch (parent, grandparent, ...), not just the first hop off a married-in member. Adding a **parent or sibling anchored on a gated-branch member** stages the new member as `visibility_status = 'pending'`: the relationship is created immediately via the ordinary `RelationshipsController` cascade (unchanged), but the new row is invisible to everyone except the requester and the family owner until decided. A new `relationship_requests` audit/notification table (RLS: select-only, visible to requester or owner; all writes go through security-definer RPCs, mirroring `family_invites`' pattern) backs three RPCs — `create_relationship_request` (atomically flips the member to pending + inserts the audit row, re-validating the anchor's gated status server-side), `approve_relationship_request` (owner-only status flip; the relationship cascade already ran at request time), and `reject_relationship_request` (owner-only; flips to rejected, then hard-deletes the pending member via the existing `remove_family_member` RPC — rejection deletes rather than keeping the profile around for resubmission). A `can_view_family_member`/`can_view_relationship` pair of security-definer predicates (modeled on `can_view_memory`) re-gate `family_members_select`/`relationships_select`, and every other SECURITY DEFINER function that reads `family_members` directly (`list_unclaimed_members` foremost, since a pending member is `is_claimed = false` by construction and would otherwise leak into invite-claim tiles) was audited and redefined with an explicit `visibility_status = 'active'` filter. Two new Edge Functions (`on-relationship-request-created`, `on-relationship-request-decided`) plus trigger functions notify the owner on submission and the requester on decision, extending `notification_type` with `relationship_request_created`/`approved`/`rejected`. New `relationships` feature slice: `RelationshipRequest`/`RelationshipRequestStatus` entities, `RelationshipRequestsRepository`, `RelationshipRequestsController`, a `PendingRequestsScreen` (owner-only queue, reachable from Settings) with `PendingRequestTile`. Tree nodes and the member profile header render a shared `MemberNodeBadges` caption — "Joined by marriage" for `marriedIn`, or "Awaiting approval" for a pending member (the two never apply to the same member at once) — alongside a new `dashed_circle_painter.dart` for pending-node styling. `visibility_status` is now a typed `FamilyMemberVisibilityStatus` enum (`active`/`pending`) in the `members` domain layer rather than a raw string. **Two follow-up fix-up migrations:** `get_elder_spotlight` is now gated to skip married-in callers entirely (its only actions walk the caller's own paternal line to suggest adding a father/spouse — exactly the flow this feature routes through Owner approval instead, so a married-in member should never see that nudge); and a bug in the original `married_in` backfill heuristic (zero parent relationships + a spouse relationship) was found and corrected — it also matched each family's **founder** (who likewise has no parent relationships), wrongly flagging founders-with-a-spouse as `married_in`/`gated_branch`. The fix-up migration identifies founders via `family_users.role = 'owner'` (there's no ownership-transfer feature, so this is a reliable 1:1 mapping), resets any founder mismarked by the earlier migrations, and re-runs the backfill excluding founders.
- **New: dedicated Members tab.** `MembersScreen` (`features/members/presentation/screens/members_screen.dart`, route `/home/members`) is now its own bottom-nav shell branch — the searchable, generation-grouped `MemberListView` inside `AppMaxWidth`, with a scroll-aware floating "Add Member" pill button (`AppPillFab` + `ScrollAwareFab`, hides while scrolling down, reappears scrolling back up). This replaces two things at once: the standalone `members_list_screen.dart` (deleted) and the Tree screen's old fourth `_TreeView.list` segment (removed from `TreeScreen`'s view switcher, which is back down to its three real tree layouts). `member_list_view.dart` is unchanged in place — same in-place name search field above the "GEN I" header — just now hosted by the new tab instead of two different screens.
- **New: tree long-press context menu.** Long-pressing a node's avatar in any of the three tree layouts (`TreeNodeWidget`/`TreeNodeWidgetHorizontal`/`TreeNodeWidgetRadial`, all Riverpod-ized to resolve permissions live) opens `showMemberContextMenu` — a custom-positioned, dimmed popup (hand-rolled via `showGeneralDialog`/`CustomSingleChildLayout` since `showMenu` has no `barrierColor`, backed by a new `AppColors.scrimBarrier` token matching Flutter's default dialog scrim) anchored at the long-press point. It offers the same actions as the member profile screen — Add Child/Sibling/Spouse/Parents (hidden once 2 parents exist), Open Profile, Mark as Past Spouse (only for a married-in member with exactly one current spouse), Unclaim (owner), Edit (Editor-role gated), Share Profile, Delete (owner, not self) — each gated by the exact same rules as `AddRelationSection`/the profile's menu button, now factored into two shared utility files (`member_profile_actions.dart`, `member_relation_options.dart`) both the profile screen and this menu call into, rather than duplicating the logic.
- **New: Export as PDF / GEDCOM.** A "Download"/"Export" bottom sheet (`TreeExportSheet`, opened from the tree screen's new action bar) offers two on-device export formats, both handed to the OS share sheet via `share_plus`: **PDF** — a vector, printable/shareable tree chart poster, built by `TreePdfRenderer`/`TreePdfLayout` from the same vertical `TreeLayoutEngine` output the on-screen tree uses (nodes as name/lifespan cards rather than avatars, connectors resampled from the same cubic-bezier curve language `TreeConnectorPainter` draws on-screen, custom Fraunces/Inter/Lora fonts loaded from a new `assets/fonts/` directory), uniformly magnified 2× for card breathing room and safety-clamped under the PDF format's ~200in page-size limit for unusually large families — **vertical-layout only** for now, horizontal/radial export isn't supported. **GEDCOM** — a standard GEDCOM 5.5.1 file (`GedcomWriter`, pure Dart, unit-testable) covering NAME/SEX/BIRT/DEAT/FAMC/FAMS/MARR/DIV only (no Nasab-specific fields like bio/phone/current-location) for maximum compatibility with Ancestry/FamilySearch/MyHeritage/Gramps and other genealogy tools. Both are driven by a new `TreeExportController` (action-only, `ref.keepingAlive`-wrapped per the auto-dispose pitfall in `CLAUDE.md`) and a `TreeExportService` (mirrors `StorageService`'s shape: typed exceptions — new `EmptyTreeExportException`/`TreeExportFailedException` — Future-returning methods), writing to a temp file via `path_provider`. No backend/RLS involvement — both formats are assembled entirely from data already fetched client-side (tree, members, relationships).
- **New: Tree action-bar redesign.** The old per-canvas `TreeZoomControls` widget (a zoom column pinned bottom-left/right-center depending on layout, `tree_zoom_controls.dart`, now deleted) is replaced by one shared, screen-owned `TreeActionBar` — a centered row of three small pill buttons: **Find** (opens the existing member-search sheet), a center **recenter/"Snap"** icon-only pill, and **Export** (opens `TreeExportSheet`, above). Since search/recenter genuinely belong to whichever per-orientation canvas (`TreeCanvas`/`TreeCanvasHorizontal`/`TreeCanvasRadial`) is currently mounted, a new `TreeCanvasActions` bridge (a `ValueNotifier<TreeCanvasActions?>` the screen owns and passes down) lets the active canvas publish its own live `openSearch`/`recenter` callbacks up to the bar, going `null` (Find/Snap render visibly disabled rather than throwing) during the brief window between one canvas disposing and its replacement mounting on an orientation switch. `AppPillFab` was extended to support this bar's needs: an optional `label` (icon-only pills), a nullable `onPressed` (renders dimmed/inert), and a `dense` flag (smaller padding/icon/text for three pills sharing one row) — all additive, existing Members/Memories tab call sites unchanged.

The radial view is **gated behind Heritage** (`PaywallSource.radialTree`). The former fourth "list" segment has moved out to its own **Members** tab (see above), so the tree screen's view switcher is back to exactly the three tree layouts. **New: improved radial engine** — the radial layout was rewritten with a native weight-proportional algorithm (`radial_tree_layout.dart`'s new physics) for more compact, balanced layouts and reduced overlapping, replacing the earlier Reingold–Tilford-inspired approach. **New: blood-relative-anchored spouse ordering** — `family_unit_graph.dart`'s couple-row ordering (`_orderFamilySegment`) now anchors each rendered row on whichever member is actually connected to the tree by blood (i.e. not `FamilyMember.marriedIn`), rather than always preferring the male member, so a row consistently reads as [past spouses] → blood relative → [current spouses] regardless of gender; falls back to the old male-preference tiebreak only when blood-status alone can't disambiguate. **Patronymic name formatting** now optionally includes the **spouse's last name** when the naming preference is enabled, so a married-in member (e.g., "Fatima al-Rashid") displays as such rather than omitting the affinal surname. Spouse relationships still carry current/past status plus a wedding date. **Search-a-member in tree** — `TreeZoomControls` was reworked from an explicit zoom-in/zoom-out/reset button column with a live zoom-percentage pill down to a simpler two-button **recenter-on-me + search** pair; pinch/drag zoom is now left entirely to the native `InteractiveViewer` (bounded by `minTreeScale`/`maxTreeScale`) instead of button-driven scale steps. Search reuses the existing shared `showMemberSelectBottomSheet` picker and, on selection, pans/recenters the canvas on that member — wired identically into all three layouts' canvases (`tree_canvas.dart`, `tree_canvas_horizontal.dart`, `tree_canvas_radial.dart`).

Row-Level Security is enabled on every table from creation. The core pattern: a user may act on a family-scoped row only if they have a `family_users` row for that `family_id`; only the `owner` role may mutate the `families` row itself or remove other members. `device_tokens`, `user_profiles`, `notifications`, and now `feedback` are user-scoped (`auth.uid()`-only) rather than family-scoped — `feedback` has select/insert-own policies only, no update/delete (users can't edit or retract a submitted request). Security-definer functions (`is_family_member`, `is_family_owner`, `can_view_memory`) are used where a policy needs to read across a table that itself has restrictive RLS.
